## 16. อ่านโค้ด Solidity ทีละส่วน: จากโครงสร้างถึงการทำงาน

### 16.1 pragma และโครงสร้างสัญญา

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract Example {
    uint256 public storedData;

    constructor() {
        storedData = 10;
    }

    function setData(uint256 newValue) public {
        storedData = newValue;
    }

    function getData() public view returns (uint256) {
        return storedData;
    }
}
```

`SPDX-License-Identifier` ระบุใบอนุญาตของ source code ส่วน `pragma` กำหนดช่วง compiler ที่ยอมรับได้ `^0.8.20` หมายถึงตั้งแต่ 0.8.20 และต่ำกว่า 0.9.0 ไม่ได้หมายความว่าเลือก compiler ให้อัตโนมัติ ชื่อ `Example` คือชื่อสัญญา และ `{ ... }` ครอบสมาชิกของสัญญา อ้างอิง [Solidity: Source File Layout](https://docs.soliditylang.org/en/latest/layout-of-source-files.html)

`storedData` ประกาศนอกฟังก์ชัน จึงเป็น state variable `public` ทำให้มี getter สำหรับอ่านค่า ส่วน constructor ตั้งค่าเริ่มต้นเป็น 10 เมื่อ deploy การเรียก setData เปลี่ยนค่าใน storage จึงต้องส่งธุรกรรมหากต้องการบันทึกผลบนเชน ขณะที่ getData อ่านข้อมูลและคืนค่าโดยไม่แก้ไข

**แนวตอบเมื่อให้อธิบายโค้ด:** “สัญญานี้เก็บจำนวนเต็มไม่ติดลบหนึ่งค่า เริ่มที่ 10 ผู้ใช้เรียก setData เพื่อเปลี่ยนค่าได้ และอ่านผ่าน getData หรือ getter ของ storedData ได้ โดย setData ไม่มีการจำกัด owner จึงเปิดให้ผู้เรียกภายนอกแก้ค่าตามกฎของฟังก์ชัน”

### 16.2 พารามิเตอร์กับค่าที่คืน

ใน `function withdraw(uint256 amount)` ค่า amount เป็นข้อมูลที่ส่งเข้าฟังก์ชัน ส่วน `returns (uint256)` ประกาศชนิดผลลัพธ์ที่ส่งกลับ และ `return` เป็นคำสั่งคืนค่าจริง ต้องแยกให้ออกระหว่างข้อมูลเข้า ข้อมูลออก และ state ที่ฟังก์ชันอ่านหรือแก้ไข

ตัวอย่าง `calculateInterest(address account)` รับ address เพื่อเลือกบัญชี อ่าน balances ของบัญชีนั้น คำนวณ และคืนจำนวน Wei โดยไม่จำเป็นต้องเป็นบัญชีเดียวกับ msg.sender เพราะใช้พารามิเตอร์ account เป็นคีย์

### 16.3 State variables ไม่เหมือน storage / memory / calldata

State / Local / Global เป็นการแบ่งบทบาทของตัวแปร ส่วน storage / memory / calldata บอกตำแหน่งข้อมูลสำหรับชนิดอ้างอิง จึงไม่ควรใช้แทนกัน เช่น local variable สามารถเป็นตัวอ้างอิงไปยัง storage ได้ ไม่ใช่ว่า local ทุกตัวต้องอยู่ใน memory เสมอ

- `storage`: ข้อมูลที่เก็บถาวรของสัญญา การแก้ผ่านตัวอ้างอิงไปยัง state ทำให้ state เปลี่ยน
- `memory`: พื้นที่ข้อมูลชั่วคราวระหว่างการเรียก ใช้กับสำเนาและผลคำนวณ
- `calldata`: พื้นที่ข้อมูลเข้าที่อ่านอย่างเดียว ใช้กับพารามิเตอร์ที่เหมาะสมเพื่อลดการคัดลอก

ส่วนนี้เป็นความรู้เสริมเพื่ออ่านโค้ด ไม่ใช่หัวข้อที่มีคำอธิบายครบในสไลด์ ตัวอย่าง `string memory` ใช้เมื่อฟังก์ชันคืนข้อความ ส่วน `uint256 amount` เป็น value type จึงไม่เขียน memory ต่อท้าย

### 16.4 ตารางวิเคราะห์ฟังก์ชันก่อนลงมือเขียนคำตอบ

| ฟังก์ชัน | รับข้อมูลอะไร | อ่านอะไร | เปลี่ยนอะไร | เงินเข้า/ออก |
|---|---|---|---|---|
| getBalance | ไม่มี | balances[msg.sender] | ไม่เปลี่ยน | ไม่มี |
| deposit | msg.value จากการเรียก | ยอดเดิมของผู้เรียก | ยอดผู้ฝาก | เข้า |
| withdraw | amount | ยอดผู้เรียก | ลด balances | ออก |
| getSystemBalance | ไม่มี | ยอด Ether ของสัญญาและ owner | ไม่เปลี่ยน | ไม่มี |
| calculateInterest | account | balances[account], rate | ไม่เปลี่ยน | ไม่มี |
| totalInterestPerYear | ไม่มี | accounts และยอดทุกบัญชี | ไม่เปลี่ยน | ไม่มี |

## 17. ตัวอย่างธนาคารครบชุดสำหรับใช้ฝึกอธิบาย

โค้ดต่อไปนี้เรียบเรียงขึ้นเพื่อรวมข้อกำหนด EasyBank และ ComplicatedBank ในสไลด์ ไม่ใช่โค้ดต้นฉบับที่ดาวน์โหลดจากผู้สอน เพิ่มการป้องกันบัญชีซ้ำและตรวจจำนวนฝาก/ถอนมากกว่าศูนย์เพื่อให้ติดตามการทำงานได้ชัดเจน

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract StudyBank {
    mapping(address => uint256) private balances;
    mapping(address => bool) private registered;
    address[] public accounts;
    uint256 public rate = 3;
    address public owner;

    constructor() {
        owner = msg.sender;
    }

    modifier onlyOwner() {
        require(msg.sender == owner, "Not owner");
        _;
    }

    function getBalance() public view returns (uint256) {
        return balances[msg.sender];
    }

    function deposit() public payable {
        require(msg.value > 0, "Zero deposit");
        if (!registered[msg.sender]) {
            registered[msg.sender] = true;
            accounts.push(msg.sender);
        }
        balances[msg.sender] += msg.value;
    }

    function withdraw(uint256 amount) public {
        require(amount > 0, "Zero withdrawal");
        require(balances[msg.sender] >= amount, "Insufficient balance");
        balances[msg.sender] -= amount;
        (bool success, ) = payable(msg.sender).call{value: amount}("");
        require(success, "Withdraw failed");
    }

    function getSystemBalance() public view onlyOwner returns (uint256) {
        return address(this).balance;
    }

    function calculateInterest(address account) public view returns (uint256) {
        return balances[account] * rate / 100;
    }

    function totalInterestPerYear() public view returns (uint256) {
        uint256 total;
        for (uint256 i = 0; i < accounts.length; i++) {
            total += calculateInterest(accounts[i]);
        }
        return total;
    }

    function getAccountCount() public view returns (uint256) {
        return accounts.length;
    }
}
```

### 17.1 เหตุผลของตัวแปรแต่ละตัว

`balances` เป็นบัญชีภายในว่าผู้ฝากแต่ละคนมีสิทธิถอนเท่าใด `registered` บันทึกว่าเคยเพิ่ม address ลง accounts แล้วหรือยัง และ `accounts` เป็นรายการสำหรับวนลูป หากไม่ใช้ registered ทุกการฝากอาจ push address ซ้ำจนดอกเบี้ยของคนเดิมถูกนับหลายรอบ

`rate` ตั้งต้นเป็น 3 ตามโจทย์ ส่วน owner บันทึกผู้ deploy การประกาศ public เปิดให้อ่านผ่าน getter แต่ในโค้ดนี้ไม่มี setter จึงไม่มีฟังก์ชันให้เปลี่ยน rate หรือ owner ภายหลัง

### 17.2 ทำไม accounts ยังมีคนที่ถอนหมดแล้ว?

โค้ดนี้เก็บประวัติผู้ที่เคยฝาก เมื่อถอนหมด ยอดเป็นศูนย์และดอกเบี้ยที่คำนวณได้เป็นศูนย์ ไม่จำเป็นต้องลบ address เพื่อให้ผลรวมถูก แต่ถ้ามีบัญชีจำนวนมาก การวนลูปก็ยังต้องผ่านรายการเหล่านั้น นี่เป็นข้อจำกัดของการออกแบบสำหรับบทเรียน

### 17.3 ทำไม getBalance ไม่รับ address?

ตาม EasyBank ต้องคืนยอดของผู้เรียก จึงใช้ msg.sender โดยตรง ส่วน calculateInterest รับ address เพื่อให้เลือกบัญชีที่ต้องการคำนวณได้ หากโจทย์ต้องการจำกัดการอ่านดอกเบี้ยให้เฉพาะเจ้าของบัญชีหรือ owner ต้องเพิ่มเงื่อนไขตามโจทย์ ไม่ควรสมมติว่า public มีการจำกัดสิทธิอยู่แล้ว

### 17.4 ขอบเขตของโปรแกรมตัวอย่าง

โปรแกรมนี้คำนวณดอกเบี้ยจากยอดปัจจุบัน ไม่มีการจ่ายดอกเบี้ยจริง ไม่มีการนับวันฝาก ไม่มีระบบกู้ยืม และไม่ได้สร้าง Ether เพิ่ม การใช้ onlyOwner กับ getSystemBalance เป็นการฝึกสิทธิเรียกฟังก์ชัน ข้อมูลยอดของ address บนเชนยังตรวจสอบได้จากภายนอก

อธิบายเพิ่มเติมเกี่ยวกับชนิดข้อมูลและตำแหน่งข้อมูลได้จาก [Solidity Types](https://docs.soliditylang.org/en/latest/types.html) และกฎฟังก์ชันจาก [Solidity Contracts](https://docs.soliditylang.org/en/v0.8.26/contracts.html)

## 18. จำลองการฝาก ถอน และดอกเบี้ย 5 บัญชี

สมมติอัตรา 3% ทุกบัญชีเริ่มจากศูนย์ ไม่มีเงินเข้าออกช่องทางอื่น และแสดงหน่วย ETH เพื่ออ่านง่าย โปรแกรมจริงเก็บหน่วย Wei

| บัญชี | ฝากเริ่มต้น | ดอกเบี้ย 3% |
|---|---|---|
| A | 1 ETH | 0.03 ETH |
| B | 2 ETH | 0.06 ETH |
| C | 3 ETH | 0.09 ETH |
| D | 4 ETH | 0.12 ETH |
| E | 5 ETH | 0.15 ETH |
| รวม | 15 ETH | 0.45 ETH |

### กรณีที่ 1: A ฝากเพิ่ม 0.5 ETH

ยอด A เปลี่ยนจาก 1 เป็น 1.5 ETH ยอดสัญญาเป็น 15.5 ETH ดอกเบี้ย A เป็น 0.045 ETH และดอกเบี้ยรวมเป็น 0.465 ETH จำนวน accounts ยังเป็น 5 เพราะ registered ของ A เป็น true แล้ว

### กรณีที่ 2: B ถอน 0.4 ETH

ยอด B ลดจาก 2 เป็น 1.6 ETH ยอดสัญญาลดเหลือ 15.1 ETH ดอกเบี้ย B เป็น 0.048 ETH และดอกเบี้ยรวมเป็น 0.453 ETH กระเป๋า B ได้รับ 0.4 ETH แต่การเปลี่ยนแปลงสุทธิของยอดในกระเป๋าผู้ส่งธุรกรรมต้องคิดค่าธรรมเนียมด้วย

### กรณีที่ 3: C ขอถอน 4 ETH ทั้งที่มี 3 ETH

require ไม่ผ่าน การถอนจึงล้มเหลว ยอด C ยังเป็น 3 ETH และยอดสัญญายังเป็น 15.1 ETH หากธุรกรรมล้มเหลวบนเชนจริง ผู้ส่งยังเสียค่าธรรมเนียมสำหรับงานที่ประมวลผลไป

### กรณีที่ 4: E ถอนหมด 5 ETH

ยอด E เป็นศูนย์ ยอดสัญญาเหลือ 10.1 ETH ดอกเบี้ยรวมเป็น 0.303 ETH และ accounts ยังมี 5 รายการ E จึงยังอยู่ในรายการแต่มีส่วนร่วมในผลรวมเป็นศูนย์

### กรณีที่ 5: ผู้ที่ไม่ใช่ owner เรียก getSystemBalance

onlyOwner ตรวจ msg.sender ไม่ตรง owner จึงปฏิเสธการเรียก การอ่านถูกจำกัดผ่านฟังก์ชันนี้ แต่ไม่เปลี่ยนความโปร่งใสของข้อมูลยอดเงินบน Blockchain

**คำตอบเชิงวิเคราะห์ที่ควรเขียนได้:** “การฝากเปลี่ยนทั้ง Ether จริงในสัญญาและยอดบัญชีภายใน การถอนที่สำเร็จลดทั้งสองอย่าง ส่วนการคำนวณดอกเบี้ยเพียงอ่านยอด ไม่เปลี่ยน Ether และไม่เพิ่มสิทธิถอน”

## 19. แบบฝึกหาข้อผิดพลาดในโค้ด

### ข้อ 1: view แต่มีการเพิ่มยอด

```solidity
function getBalance() public view returns (uint256) {
    balances[msg.sender] += 1;
    return balances[msg.sender];
}
```

**แนวตอบ:** การเพิ่มยอดเป็นการแก้ state จึงขัดกับ view และ compile ไม่ผ่านในบริบทนี้ ถ้าต้องการอ่านยอดตามชื่อฟังก์ชันให้ลบคำสั่ง `+= 1` หากโจทย์ต้องการเพิ่มยอดจริงต้องเปลี่ยนการออกแบบและส่งธุรกรรม พร้อมตรวจสิทธิ ไม่ใช่เปลี่ยน keyword แล้วจบโดยไม่วิเคราะห์เจตนา

### ข้อ 2: เพิ่มทุก address ทุกครั้งที่ฝาก

```solidity
function deposit() public payable {
    accounts.push(msg.sender);
    balances[msg.sender] += msg.value;
}
```

**แนวตอบ:** ยอดเงินรายบัญชีเพิ่มถูก แต่รายการ accounts มี address ซ้ำ ผู้ฝากสองครั้งอาจถูกนับดอกเบี้ยสองรอบเมื่อวนลูป แก้โดยตรวจการลงทะเบียนก่อน push ใช้ mapping ของ bool หรือวิธีตรวจสมาชิกที่เหมาะสม

### ข้อ 3: ขอบเขต loop เกินสมาชิก

```solidity
for (uint256 i = 0; i <= accounts.length; i++) {
    total += calculateInterest(accounts[i]);
}
```

**แนวตอบ:** เมื่อ i เท่ากับ length จะอ่าน index ที่ไม่มีอยู่ เพราะสมาชิกสุดท้ายมี index length − 1 ต้องเปลี่ยนเป็น `<` และ array ว่างต้องไม่วนลูปเลย

### ข้อ 4: โอนเงินให้ owner แทนผู้ถอน

```solidity
balances[msg.sender] -= amount;
(bool success, ) = payable(owner).call{value: amount}("");
require(success, "Failed");
```

**แนวตอบ:** ลดสิทธิถอนของผู้เรียก แต่ส่งเงินให้ owner จึงผิดเจตนาของการถอนรายบัญชี ต้องเลือกผู้รับเป็น msg.sender และต้องมี require ตรวจยอดก่อนลดด้วย

### ข้อ 5: คิดดอกเบี้ยกลับลำดับ

```solidity
return balances[account] / 100 * rate;
```

**แนวตอบ:** การหารจำนวนเต็มก่อนคูณอาจตัดเศษเร็ว ทำให้ผลคลาดเคลื่อนเพิ่ม ควรคูณ rate ก่อนหาร 100 ภายใต้ช่วงค่าที่ไม่ overflow เช่นเงินต้น 199 Wei อัตรา 3% สูตรคูณก่อนให้ 5 Wei ขณะที่หารก่อนให้ 3 Wei

### ข้อ 6: ทึกทักว่ามี getter แล้วมี setter

```solidity
uint256 public rate = 3;
```

**แนวตอบ:** public ทำให้เกิด getter สำหรับอ่าน rate ไม่ใช่ setter ถ้าต้องการเปลี่ยนอัตราต้องเขียนฟังก์ชันเพิ่มและกำหนดผู้ที่เปลี่ยนได้ เช่น onlyOwner

## 20. Enum: อ่านเงื่อนไขก่อนเปลี่ยนสถานะ

```solidity
enum Status { Pending, Active, Completed, Canceled }
Status public currentStatus;

function activate() public {
    require(currentStatus == Status.Pending, "Invalid state");
    currentStatus = Status.Active;
}

function complete() public {
    require(currentStatus == Status.Active, "Invalid state");
    currentStatus = Status.Completed;
}
```

เริ่มต้น enum มีค่าแรกคือ Pending หากยังไม่ได้กำหนดค่าอื่น การเรียก complete ตั้งแต่ Pending จะถูกปฏิเสธ ต้อง activate ให้เป็น Active ก่อน จากนั้นจึง complete ได้ ถ้าเรียก activate หลัง Completed จะไม่ผ่านเงื่อนไข

การมีชื่อ Canceled ใน enum ไม่ได้ทำให้เกิดฟังก์ชันยกเลิกอัตโนมัติ และในตัวอย่างนี้ไม่ได้จำกัด owner ดังนั้นใครที่เข้าถึง public function ก็อาจเปลี่ยนสถานะได้เมื่อเงื่อนไขผ่าน หากโจทย์ต้องการให้เฉพาะผู้จัดการเปลี่ยนสถานะ ต้องเพิ่มการตรวจสิทธิด้วย

**แนวตอบอัตนัย:** “enum ทำให้ชุดสถานะมีชื่อและจำกัดชนิดค่าที่เลือกได้ แต่กฎการเปลี่ยนสถานะและผู้มีสิทธิเปลี่ยนเป็นอีกส่วนหนึ่ง ต้องเขียนเงื่อนไขตรวจอย่างชัดเจน”

## 21. แนวตอบอัตนัยแบบยาวพร้อมโครงคะแนน

เกณฑ์ด้านล่างเป็นรายการตรวจคำตอบสำหรับฝึกเอง ไม่ใช่เกณฑ์ให้คะแนนจริงของผู้สอน

### ข้อ A: อธิบายระบบฝากถอนโดยใช้ mapping และความสัมพันธ์กับ Ether จริง

**ตัวอย่างคำตอบ:** สัญญาใช้ mapping เชื่อม address ของผู้ฝากกับยอดเงินในหน่วย Wei ฟังก์ชัน deposit เป็น payable เพื่อรับ Ether ที่ส่งมา แล้วใช้ msg.sender ระบุเจ้าของยอดและ msg.value เพิ่ม balance ของผู้เรียก ฟังก์ชัน getBalance อ่านค่าของผู้เรียกและเป็น view ส่วน withdraw รับ amount ตรวจว่ายอดพอ ลด balance ก่อนส่ง Ether กลับ และตรวจความสำเร็จของการโอน ถ้าโอนไม่สำเร็จให้ revert ยอดใน mapping คือบัญชีสิทธิถอน ขณะที่ address(this).balance คือ Ether จริงทั้งหมดในสัญญา เช่น A ฝาก 1 ETH และ B ฝาก 2 ETH จะมียอดรายคน 1 และ 2 ETH และยอดรวม 3 ETH ก่อนมีรายการอื่น

**ตรวจให้ครบ:** mapping, หน่วย Wei, payable, msg.sender, msg.value, require, ลำดับถอน, ความต่างของยอดสองชนิด

### ข้อ B: อธิบายการคำนวณดอกเบี้ยรวมและปัญหาบัญชีซ้ำ

**ตัวอย่างคำตอบ:** คำนวณดอกเบี้ยรายบัญชีด้วยเงินต้นคูณ rate แล้วหาร 100 โดยอ่านเงินต้นจาก balances[account] จากนั้นเก็บรายการผู้ฝากใน accounts เพราะ mapping ไม่ให้รายการคีย์สำหรับวนลูปโดยตรง ฟังก์ชันรวมดอกเบี้ยสร้าง local variable total แล้ววนตั้งแต่ index 0 จนก่อน length เรียก calculateInterest ของแต่ละบัญชีและสะสมผล ต้องป้องกันการเพิ่ม address ซ้ำมิฉะนั้นคนที่ฝากหลายครั้งถูกนับซ้ำ เช่น A มี 1 ETH และ B มี 2 ETH ที่ 3% ให้ผลรวม 0.09 ETH การคืนผลรวมนี้ไม่ใช่การจ่ายดอกเบี้ยและยังไม่ได้คิดระยะเวลาฝากจริง

**ตรวจให้ครบ:** สูตร, array, mapping วนคีย์ไม่ได้โดยตรง, loop, total, บัญชีซ้ำ, ตัวอย่าง, คำนวณไม่เท่ากับจ่าย

### ข้อ C: อธิบายการควบคุมสิทธิด้วย constructor และ modifier

**ตัวอย่างคำตอบ:** constructor ทำงานครั้งเดียวตอนสร้างสัญญาและเก็บ msg.sender เป็น owner เพื่อระบุผู้จัดการ modifier onlyOwner ใช้ require เปรียบเทียบผู้เรียกกับ owner ถ้าไม่ตรงจะ revert ส่วน _; เป็นตำแหน่งดำเนินคำสั่งของฟังก์ชันหลังตรวจเงื่อนไขในตัวอย่างนี้ การนำ modifier ไปใช้กับหลายฟังก์ชันช่วยให้เงื่อนไขเหมือนกันและลดการเขียนซ้ำ อย่างไรก็ตามการจำกัดฟังก์ชันอ่านยอดไม่ได้ซ่อนข้อมูลจากผู้ตรวจสอบเชน และ private ไม่ใช่กลไกเข้ารหัสข้อมูล

**ตรวจให้ครบ:** ทำงานครั้งเดียว, ผู้ deploy, require, revert, _;, ใช้ซ้ำ, visibility ต่างจากความลับ

### ข้อ D: อธิบายความน่าเชื่อถือของ Blockchain และข้อจำกัด

**ตัวอย่างคำตอบ:** Blockchain จัดข้อมูลเป็นบล็อกที่เชื่อมกันด้วย hash และกระจายสำเนาให้หลายโหนด การแก้ข้อมูลเก่าทำให้ hash เปลี่ยนและกระทบความเชื่อมโยงของบล็อกถัดไป อีกทั้งเครือข่ายใช้ consensus ตัดสินประวัติที่ยอมรับร่วมกันจึงทำให้การแก้ย้อนหลังทำได้ยาก ลายมือชื่อดิจิทัลช่วยตรวจสิทธิของผู้ส่งและความครบถ้วนของธุรกรรม แต่ระบบไม่ได้รับรองว่าข้อมูลภายนอกที่ป้อนเข้าเป็นจริงเสมอ เช่นบันทึกสถานะสินค้าผิดก็ยังเป็นข้อมูลผิดที่ตรวจสอบย้อนหลังได้ ความโปร่งใสและการกระจายสำเนาจึงต้องใช้ร่วมกับการออกแบบแหล่งข้อมูลและสิทธิที่เหมาะสม

**ตรวจให้ครบ:** บล็อก, hash, สำเนา, consensus, ลายมือชื่อ, ข้อมูลต้นทาง, ข้อจำกัด

## 22. แบบฝึกคำนวณพร้อมวิธีทำ

### โจทย์ 1: ค่าธรรมเนียมธุรกรรม

ธุรกรรมใช้ 80,000 Gas ราคาจ่ายจริง 15 Gwei ต่อ Gas ค่าธรรมเนียม = 80,000 × 15 = 1,200,000 Gwei = **0.0012 ETH** ต้องแสดงการแปลงหน่วยและอย่าสับสน Gwei กับ Wei

### โจทย์ 2: เงินต้นกับดอกเบี้ย

ยอดบัญชี 4 ETH อัตรา 3% → 4 × 3 / 100 = **0.12 ETH** ถ้าใช้หน่วย Wei เงินต้นคือ 4 × 10¹⁸ Wei ผลคือ 1.2 × 10¹⁷ Wei ไม่จำเป็นต้องแปลงเป็น ETH ในสัญญา

### โจทย์ 3: ฝากแล้วถอน

A ฝาก 0.8 ETH อีกครั้ง 0.7 ETH แล้วถอน 0.4 ETH ยอดใน mapping เหลือ **1.1 ETH** ดอกเบี้ยตาม rate 3% เท่ากับ **0.033 ETH** ค่าธรรมเนียมกระทบกระเป๋าที่ส่งธุรกรรม ไม่ได้ถูกลบจาก balances โดยโค้ดตัวอย่างเอง

### โจทย์ 4: หาเหตุผลของผลต่างจากการปัดเศษ

สองบัญชีมีเงินต้นบัญชีละ 34 Wei อัตรา 3% แต่ละบัญชีได้ 1 Wei ผลรวมดอกเบี้ยรายบัญชีเป็น 2 Wei หากรวมเงินต้นก่อนเป็น 68 Wei แล้วคิด 3% ก็เป็น 2 Wei เช่นกันในตัวอย่างนี้ แต่สองบัญชีละ 20 Wei จะได้รายคน 0 Wei รวมเป็น 0 Wei ขณะที่รวมเงินต้นก่อน 40 Wei แล้วคิด 3% ได้ 1 Wei จึงไม่ควรสรุปว่าสองวิธีเท่ากันเสมอ เพราะมีการตัดเศษจำนวนเต็ม

### โจทย์ 5: หน่วย Bitcoin

250 sats = 250 / 100,000,000 BTC = **0.0000025 BTC** หน่วย satoshi เป็นของ Bitcoin ส่วน Wei และ Gwei เป็นหน่วย Ether อย่าสลับระบบหน่วย

### เช็กลิสต์ก่อนส่งคำตอบอัตนัย

- ตอบตรงคำถามว่าให้นิยาม เปรียบเทียบ อธิบายโค้ด หรือวิเคราะห์ข้อผิดพลาด
- ระบุว่าฟังก์ชันอ่านหรือแก้ state และมี Ether เข้าออกหรือไม่
- ใช้ msg.sender และ msg.value ถูกความหมาย
- ใส่หน่วยของเงินและตัวเลขที่คำนวณได้
- แยกสิทธิเรียกฟังก์ชันออกจากความเป็นส่วนตัวของข้อมูล
- ไม่อ้างว่าดอกเบี้ยคำนวณแล้วจ่ายอัตโนมัติ หรือ transaction hash ยืนยันความสำเร็จ
- ยกตัวอย่างสั้นที่พิสูจน์คำอธิบาย ไม่เพิ่มข้อสมมติที่ขัดกับโจทย์
